# CROWN 신경망 검증을 위한 GPU 가속 및 메모리 계층 최적화 기법 연구

## 제1장 서론

안테나 선택 신경망의 검증 계산을 하드웨어에서 수행하려면 계산 결과의 정확성과 실행 비용을 함께 고려해야 한다. 이 연구는 CROWN 검증 계산을 GPU로 이식하고, 실시간 활용 가능성을 탐색하는 과정에서 나타난 성능 특성을 다룬다. 연구의 출발점은 GPU 이식이 곧바로 실행 시간 감소로 이어지지 않았다는 관찰이다. 초기 CPU·GPU 비교 이후 메모리 관리, 데이터 복사, 커널 실행 방식을 바꾸는 과정에서 실행 시간이 달라졌으며, 이 변화는 연산 병렬화와 그 주변 비용을 함께 검토할 필요성을 제기한다.

정방향 통과와 backward 계산이 이어지는 실행 흐름에서는 중간 결과를 어디에 보관하고 언제 복사하는지, 버퍼를 다시 사용할 수 있는지, 커널 호출을 어떻게 구성하는지가 주요 설계 대상이 된다. 본 연구는 이러한 요소를 메모리·데이터 이동과 커널·실행 최적화로 나누어 정리한다. 목표는 기록된 구현 변경과 성능 관측을 연결하여 GPU 검증 계산의 개선 방향을 제시하는 것이다. 여러 변경이 함께 적용된 실험이 포함되어 있으므로, 특정 기법 하나의 효과를 입증하는 것과 구현 전체에서 관측된 변화를 구분한다.

본 연구의 기여는 구현과 평가의 두 측면에 있다. 구현 측면에서는 버퍼 재사용, 불필요한 복사 제거, 커널 통합 등 GPU 실행 경로의 변경을 체계적으로 설명한다. 평가 측면에서는 단일 실행 지연, bound 구간의 평균 가속비, 준비된 데이터의 배칭 처리량을 구분하여 성과의 의미를 해석한다. 대표적으로 후기 단일 실행에서는 13.939ms가 관측되었고, 별도의 sparse.py 대비 평균 bound 계산 비교에서는 forward 5.32배와 backward 5.30배가 표기되었다. 전자는 초기화·예열 조건을 포함한 특정 실행의 관측이며, 후자는 별도 비교표의 구간별 지표다. 실시간 활용 가능성은 실제 입력 조건에서의 추가 평가가 필요한 과제로 남는다.

이하 3장에서는 배경 개념과 기존 계산 흐름을 바탕으로 문제를 정의한다. 4장은 GPU 실행 경로의 변경을 설명하고, 5장은 실험 조건에 따른 결과와 해석 한계를 논한다. 6장에서는 주요 발견과 후속 검증 과제를 정리한다. 관련 연구는 2장에 별도로 보완한다.

## 제2장 관련 연구

## 제3장 배경 지식 및 문제 정의

### 3.1 배경 개념

이 연구의 대상은 안테나 선택 신경망에 대한 CROWN 검증 계산이다. 계산 흐름에는 신경망의 정방향 통과와 backward 계산, bound 계산이 포함된다. 이 계산을 GPU에서 실행하는 구현을 대상으로, 계산 연산과 그 연산을 지원하는 메모리·데이터 이동 경로를 함께 살펴본다. [확인 필요: 검증 계산의 입력·출력 및 수식적 정의]

GPU 구현에서는 연산 시간 외에 메모리 준비와 복사, 커널 실행에 드는 비용도 관측 범위에 포함될 수 있다. 따라서 계산 결과를 얻는 데 걸린 시간을 해석하려면 측정 구간에 초기화와 예열이 포함되는지, 어떤 연산 구간을 비교하는지 구분해야 한다. 단일 실행의 지연과 여러 입력을 처리하는 배칭의 소요 시간 역시 서로 다른 평가 지표다.

### 3.2 기존 계산 흐름

초기 구현의 비교 대상은 정방향 통과와 backward 계산을 포함한 CPU 실행 및 GPU 실행이다. 초기 비교에서는 GPU 실행이 CPU 실행보다 오래 걸리는 사례가 관측되었다. 이는 연산을 GPU로 옮긴 구현을 평가할 때 계산 외의 실행 비용도 검토해야 한다는 문제를 제기한다.

이후 구현에서는 메모리 풀과 벡터 연산, 복사 경로, 커널 구성에 관한 변경이 시험되었다. 이 과정은 단일 변경을 같은 조건에서 반복 비교한 실험만으로 구성되어 있지 않다. 따라서 기존 흐름과 개선 흐름을 비교할 때는 어떤 버전의 어떤 구간을 측정했는지가 중요하다. 구체적인 구현 변경은 4장에서, 수치와 측정 조건은 5장에서 다룬다.

### 3.3 문제 정의

본 연구가 다루는 첫 번째 문제는 정방향 통과와 backward 계산을 포함한 GPU 실행 흐름에서 불필요한 할당·복사와 중복 연산을 줄이는 것이다. 메모리를 재사용하는 방식, 데이터의 상주와 전송 경로, 커널의 구성과 호출 단위를 주요 변경 대상으로 삼는다.

두 번째 문제는 구현 변경에 따른 관측을 적절한 범위에서 해석하는 것이다. 단일 실행 지연, sparse.py 대비 bound 구간의 평균 가속비, 준비된 데이터의 배칭 처리량을 별도로 평가하고, 초기화·예열 경계가 다른 결과를 같은 조건의 비교로 취급하지 않는다.

이 연구의 범위는 GPU 이식 및 최적화 과정의 구현과 성능 관측을 정리하는 데 있다. 전체 입력의 검증 결과 일치 여부, 개별 변경의 독립 효과, 실제 입력 도착 조건에서의 지연은 추가 검증 과제다. 이 조건을 전제로 계산 경로의 변경과 실시간 활용 가능성 사이의 관계를 논한다.

## 제4장 연구 방법론 및 커널 최적화 설계

### 4.1 전체 구조

GPU 가속 파이프라인은 정방향 통과와 backward 계산을 포함한 검증 실행을 대상으로 한다. 구현 변경은 메모리·데이터 이동과 커널·실행 최적화로 나누어 설명한다. 전자는 메모리 할당과 데이터 상주, 복사 경로, 버퍼 재사용을 다루고, 후자는 커널 통합과 중복 연산 제거, 실행 단위의 구성을 다룬다.

이 구분은 여러 시점에 수행된 구현 변경을 정리하기 위한 것이다. 모든 변경이 처음부터 하나의 통합 설계로 적용된 것은 아니며, 각 변경의 성능 관측과 해석 조건은 5장에서 제시한다. 이하에서는 변경 대상과 의도를 중심으로 GPU 실행 경로를 설명한다.

### 4.2 메모리·데이터 이동

메모리·데이터 이동 설계에서는 할당·상주·버퍼 재사용과 복사 경로의 변경을 다룬다.

메모리 풀은 할당과 해제를 반복하지 않도록 도입된 요소이다. 자료에는 cuBLAS 행렬곱, 메모리 풀, CPU 벡터 연산을 함께 적용한 버전에서 실행 시간이 줄어들었지만 여전히 CPU보다 느리다는 기록이 있다. 이 시점의 수치는 메모리 풀 하나의 독립 효과로 귀속하지 않으며, 여러 변경이 함께 적용된 결과로 해석해야 한다. 메모리 풀은 이후 alpha/beta의 메모리 풀 유지, forward 입력 버퍼의 backward 재사용 같은 변경과 결합되어 사용되었다.

데이터 상주 방식도 중요한 변경 대상이었다. 가중치 양·음수부를 GPU에 상주시키는 시도가 있었고, zero 초기화의 CPU 실행과 관련된 처리도 검토되었다. 이러한 변경은 가중치를 매번 전송하지 않고 재사용 가능한 상태로 두는 방향을 지향한다. 다만 자료에는 상주 자체가 독립적으로 어느 정도의 효과를 냈는지 분리해 기록한 내용은 없으므로, 상주와 다른 변경을 합쳐 해석하지 않는다.

복사 경로 제거는 실행 시간 감소에 크게 기여한 요소로 기록되어 있다. 메모리 풀과 예열 이후 zero 초기화의 CPU 실행, 결과 버퍼의 불필요한 복사 제거, 가중치 양·음수부 상주, forward 단계의 D2H 복사 제거가 시도되었고, forward 복사 제거 이후 실행 시간이 크게 줄어든 기록이 있다. 결과 버퍼가 저장될 행렬과 벡터까지 불필요하게 memcpy하던 부분을 제거하면서 추가 감소가 있었다고 기록되어 있으며, 이후 중간 결과 복사 제어로 memcpy 호출 횟수가 줄어든 관측도 있다. 다만 서로 다른 버전을 합쳐 단일 최적화의 효과라고 쓰지 않으며, memcpy 호출 횟수 감소와 커널 호출 감소를 동일한 수치로 다루지 않는다.

forward와 backward 사이의 버퍼 재사용도 데이터 이동 최적화의 한 축이다. forward 입력 버퍼를 backward에서 재사용하여 H2D 복사를 제거하는 방향이 기록되었고, 이는 후기 단일 실행 관측값과 함께 언급된다. 이 변경은 복사 경로를 줄이는 의도를 가지지만, 초기 실행 관측값과 동일한 초기화·예열·측정 경계에서 얻은 값이라고 가정하지 않는다. 따라서 버퍼 재사용의 효과는 복사 제거의 맥락 안에서 설명하되, 측정 조건이 달라질 수 있음을 함께 명시한다.

데이터 전송 최적화와 관련해 cudaGraph와 배칭도 검토되었다. 수십 번의 커널 호출을 graph로 묶는 방법이 기록되었고, 추론과 bound를 따로 캡처한 실험에서는 시간 감소가 메모되었다. 준비된 데이터셋의 배칭은 단일 스트림보다 시간이 줄어들었다고 기록되어 있으나, 원문에 약·정도 표현이 있으므로 확정 평균으로 격상하지 않는다. 또한 배칭 처리량의 개선을 단일 요청 응답 지연이나 실시간성 입증으로 확대하지 않는다. 실제 입력 환경에서는 데이터셋을 꽉 채워 넣기 어렵다는 점도 함께 기록되어 있어, 배칭 효과는 준비된 데이터 조건과 실제 입력 조건을 구분해 해석해야 한다.

이 층위에서 시도했지만 효과가 뚜렷하지 않았거나 조건 의존적으로 나타난 요소도 있다. cuBLAS와 cuSPARSE는 실험되었지만 당시 모델 크기와 호출 패턴에서는 느려져 기준 코드에 포함하지 않았다. 이 결과의 적용 범위는 시험된 모델 크기와 호출 패턴에 한정된다. pinned memory, cudaEvent 계측, 크기 계산, 복사, 검증 자료구조 등의 변경이 함께 존재한 실험도 있어, 특정 요소 하나가 실패 원인이라고 단정하지 않는다.

### 4.3 커널·실행 최적화

커널·실행 최적화는 커널 및 라이브러리 활용, 커널 퓨전, 실행 흐름과 런타임 최적화를 포함한다. 이 층위에서는 계산 병렬화를 적용하는 방식과 함께 커널 호출 배치, 중간 결과 처리, 연산 통합, 실행 경계 제어가 어떻게 이루어졌는지 기술한다.

커널 퓨전과 set_shape 내장은 커널 호출과 실행 흐름을 정리하기 위한 변경으로 기록되어 있다. 자료에는 커널 퓨전과 set_shape 내장 후 최저 약 21ms가 기록되었고, alpha/beta의 메모리 풀 유지 후 약 21.0ms가 기록되었다. 중간 결과 복사 제어 후에는 약 17ms가 기록되었다. 이 값도 여러 변경이 결합된 구현의 관측으로 해석한다. 이러한 값은 서로 다른 시점에 관측된 것이며, 최저 관측값을 반복 실험 평균으로 표현하지 않는다. 커널 퓨전으로 호출을 통합한 기록과, backward_bound_gpu에서 affine 중복 계산을 없애면서 커널 함수 두 개를 줄였다는 기록도 있으나, 전체 커널 호출 수가 특정 비율로 감소했다는 근거는 없다.

affine 연산의 GPU 내부 통합은 GPU→CPU→GPU 경로를 줄이기 위한 변경이었다. 자료에는 후속 affine 연산의 GPU 내부 통합이 GPU→CPU→GPU→CPU 불필요한 복사를 줄인다고 기록되어 있다. 이는 연산 자체를 GPU 안에 머무르게 하여 데이터 이동 경계를 줄이려는 시도로 볼 수 있다. 다만 이 통합이 다른 복사 제거나 메모리 풀 유지와 완전히 분리되어 평가되었다고 단정하지 않는다.

실행 흐름과 런타임 최적화에서는 cudaGraph를 활용한 커널 호출 묶음과 배칭 처리가 함께 검토되었다. graph로 수십 번의 커널 호출을 묶는 방법이 기록되었고, 준비된 데이터셋의 배칭은 단일 스트림보다 시간이 줄어들었다고 기록되어 있다. 그러나 이 개선은 준비된 데이터 조건에 의존하며, 실제 입력 도착 조건에서의 단일 요청 지연이나 꼬리 지연을 곧바로 입증하지는 않는다. 또한 cudaEvent 추가나 여러 변경이 함께 작용한 실험도 있어, graph 단일 적용의 효과를 다른 변경과 분리해 해석할 때는 주의가 필요하다. 자료에는 forward에서는 전체적 추론·bound·검증 측면에서 graph 단일 적용이 우수하다는 기록과, backward에서는 total 시간이 비슷하다는 기록이 함께 있어, 실행 방향에 따라 양상이 다를 수 있음을 보여준다. 다만 이 관측은 cudaEvent 추가, 크기 계산, 복사, 검증 자료구조 등 여러 변경이 함께 작용한 실험에서 나온 것이므로, graph 자체의 효과로 단정하지 않는다.

외부 라이브러리 활용은 이 층위에서도 조건 의존적으로 나타났다. cuBLAS와 cuSPARSE는 실험되었지만 당시 모델 크기와 호출 패턴에서는 느려져 기준 코드에 포함하지 않았다. 따라서 라이브러리 활용이 항상 유효하다거나, 연구에서 배제되었다고 해서 일반적으로 열등하다고 쓰지 않는다. 이 점은 커널·실행 최적화가 특정 모델과 호출 패턴에 맞춰 설계되어야 함을 보여준다.

시도했지만 효과가 없었던 방법이나 한계가 분명한 방법도 함께 정리한다. FP32로 바꿔 본 사실과 전체 입력 중 일부 검증 결과가 달라질 수 있어 재시험과 분석이 필요하다는 기록이 있으나, 이는 실제 오류 개수나 실패율을 측정한 결과가 아니라 가능성 수준의 후속 과제이다. 실행 시간 스파이크와 예열 조건의 불확실성도 남아 있어, 측정 범위와 예열 조건을 분리하고 여러 변경의 효과를 통제하는 것이 필요하다. 따라서 커널·실행 최적화의 성과는 특정 관측값을 반복 평균이나 전체 서비스 처리량으로 확대하지 않고, 관측 조건과 함께 해석한다.

이 층위의 최적화는 계산 병렬화 자체보다 커널 호출 경계, 중간 결과 처리, 연산 통합, 실행 흐름 제어가 실행 시간에 크게 영향을 미친다는 점을 보여준다. 다만 여러 변경이 함께 적용된 실험이 많아, 개별 최적화의 효과를 분리해 말하기는 어렵다. 이에 따라 후속 과제에서는 동일 측정 경계의 재측정, 전체 입력의 수치 정확성 검증, 실제 입력 도착 조건에서의 지연 평가가 필요하다.

## 제5장 실증 평가 및 결과 고찰

### 5.1 실험 설계

평가 대상은 정방향 통과와 backward 계산을 포함한 CPU·GPU 실행, sparse.py와 CUDA의 bound 계산 구간, 그리고 준비된 데이터의 배칭 실행이다. 단일 실행의 지연, 구간별 평균 가속비, 배칭 처리에 걸린 시간을 구분하여 결과를 제시한다. 평균 bound 계산 비교는 n=5 기준이며, 다른 관측의 반복 횟수는 이 값으로 대신하지 않는다.

실험 기록에는 버전에 따라 메모리 풀과 예열, 복사 경로, 계측 방식의 차이가 있다. 따라서 각 결과에 측정 범위를 함께 설명하고, 초기화·예열 경계가 같다고 확인되지 않은 실행 사이에서는 동일 조건의 가속비를 계산하지 않는다. 여러 변경이 결합된 관측과 약·정도로 기록된 시간은 해당 조건을 명시하여 제시한다.

### 5.2 결과 및 분석

초기 실행 관측에서는 정방향 통과와 backward 계산을 포함한 CPU 실행과 GPU 실행의 elapsed time이 함께 기록되었다. 동일 초기 비교 화면에서 CPU 101.237800ms, GPU 353.057200ms가 기록되어 있으며, 이는 신경망 정방향 통과와 backward 계산을 포함한 초기 실행 관측값이다. 이 값은 예열이나 측정 경계 조정이 적용된 후기 결과와 동일한 조건이라고 가정하지 않는다.

이후 여러 변경이 결합되면서 실행 시간은 크게 달라졌다. cuBLAS 행렬곱, 메모리 풀, CPU 벡터 연산을 함께 적용한 버전에서는 229.691ms가 기록되었고, 이는 100ms 정도 줄었지만 여전히 CPU보다 느리다는 기록으로 남아 있다. 이 수치는 메모리 풀 하나의 독립 효과로 귀속하지 않으며, 여러 변경이 함께 적용된 결과로 해석해야 한다. 예열과 측정 경계를 재검토한 결과, 실제 가중치 재사용 없이도 예열과 측정 범위 변화로 약 50ms가 줄어든 사실이 기록되어 있어, 초기화 비용이 측정 밖으로 옮겨진 효과와 계산 자체가 빨라진 효과를 구별해야 한다.

메모리 풀과 예열 이후 zero 초기화의 CPU 실행, 결과 버퍼의 불필요한 복사 제거, 가중치 양·음수부 상주, forward 단계의 D2H 복사 제거가 시도되었고, forward 복사 제거 이후 약 64ms가 기록되었다. 결과 버퍼가 저장될 행렬과 벡터까지 불필요하게 memcpy하던 부분을 제거하면서 추가 감소가 있었다고 기록되어 있으며, 이후 중간 결과 복사 제어로 memcpy 호출 횟수가 줄어든 관측도 있다. 다만 서로 다른 버전을 합쳐 단일 최적화의 효과라고 쓰지 않으며, memcpy 호출 횟수 감소와 커널 호출 감소를 동일한 수치로 다루지 않는다.

커널·실행 배치와 관련된 관측에서는 커널 퓨전과 set_shape 내장 후 최저 약 21ms, alpha/beta의 메모리 풀 유지 후 약 21.0ms가 기록되었다. 중간 결과 복사 제어 후에는 약 17ms가 기록되었다. 이 값도 여러 변경이 결합된 구현의 관측으로 해석한다. 후속 affine 연산의 GPU 내부 통합은 GPU→CPU→GPU→CPU 불필요한 복사를 줄인다고 기록되어 있고, backward_bound_gpu에서 affine 중복 계산을 없애면서 커널 함수 두 개를 줄였다는 기록과 커널 퓨전으로 호출을 통합한 기록도 있다. 그러나 전체 커널 호출 수가 특정 비율로 감소했다는 근거는 없으며, 최저 관측값을 반복 실험 평균으로 표현하지 않는다.

후기 단일 샘플 실행에서는 forward 입력 버퍼를 backward에서 재사용하고 초기 상태를 GPU에서 생성한 버전의 화면에 13.939000ms가 기록되어 있다. 화면에는 mempool + warmup이 명시되어 있으며, forward 단계의 입력 버퍼를 backward에서 재사용하여 H2D 복사를 제거하는 방향이 함께 언급된다. 이 값은 초기 관측값과 초기화·예열·측정 경계가 달라질 수 있으므로, 353.0572ms에서 13.939ms로의 관측 변화는 제시할 수 있지만 이를 계산 커널만의 향상이나 동일 조건 CPU 대비 가속비로 단정하지 않는다.

구간별 비교로는 sparse.py와 CUDA의 평균 bound 계산 시간이 별도로 기록되어 있다. n=5 기준 평균 bound 계산 비교에서 forward는 sparse.py 6.951ms, CUDA 1.307ms로 표기 가속비 5.32배, backward는 sparse.py 8.044ms, CUDA 1.519ms로 표기 가속비 5.30배로 나타난다. 추론+bound+검증 비교는 각각 4.86배와 4.89배로 별도 표기되어 있다. 이 가속비는 FP32/FP64 비교가 아니며, 13.939ms의 비교비와도 다르다. 특정 구간의 가속비를 전체 서비스의 처리량이나 실시간 보장으로 확대하지 않는다.

배칭과 cudaGraph 관련 기록은 준비된 데이터 조건에 의존한다. 수십 번의 커널 호출을 graph로 묶는 방법이 기록되었고, 추론과 bound를 따로 캡처한 실험에서는 약 400초 감소로 메모되었다. 준비된 데이터셋의 배칭은 단일 스트림보다 시간이 줄어들었다고 기록되어 있으며, 약 25분에서 8분으로 줄었다는 표현이 있다. 다만 원문에 약·정도 표현이 있으므로 확정 평균으로 격상하지 않으며, 배칭 처리량의 개선을 단일 요청 응답 지연이나 실시간성 입증으로 사용하지 않는다. 실제 입력 환경에서는 데이터셋을 꽉 채워 넣기 어렵다는 점도 함께 기록되어 있어, 배칭 효과는 준비된 데이터 조건과 실제 입력 조건을 구분해 해석해야 한다.

단일 스트림 입력 복사 실험에서는 교란 요인도 나타났다. forward graph 기본 실행 약 983초 대비 필요한 크기 계산·복사 등을 적용한 실행 약 1055초의 지연이 기록되었고, 이후 평균 비교에서는 graph 기본 버전과 여러 변경을 합친 버전의 forward/backward 양상이 달랐다. forward에서는 전체적 추론·bound·검증 측면에서 graph 단일 적용이 우수하다는 기록과, backward에서는 total 시간이 비슷하다는 기록이 함께 있어, 실행 방향에 따라 양상이 다를 수 있음을 보여준다. 다만 이 관측은 cudaEvent 추가, 크기 계산, 복사, 검증 자료구조 등 여러 변경이 함께 작용한 실험에서 나온 것이므로, graph 자체의 효과로 단정하지 않는다.

외부 라이브러리 적용 범위는 조건 의존적으로 나타났다. cuBLAS와 cuSPARSE는 실험되었지만 당시 모델 크기와 호출 패턴에서는 느려져 기준 코드에 포함하지 않았다고 명시되어 있다. 이 결과의 적용 범위는 시험된 모델 크기와 호출 패턴에 한정된다. 수치 정확성과 재현성 조건도 아직 완전히 정리되지 않았다. FP32로 바꿔 본 사실과 전체 입력 중 일부 검증 결과가 달라질 수 있어 재시험과 분석이 필요하다는 기록이 있으나, 이는 실제 오류 개수나 실패율을 측정한 결과가 아니라 가능성 수준의 후속 과제이다. 실행 시간 스파이크와 예열 조건의 불확실성도 남아 있어, 측정 범위와 예열 조건을 분리하고 여러 변경의 효과를 통제하는 것이 필요하다.

### 5.3 한계와 미해결 문제

이 연구의 가장 큰 한계는 여러 변경이 함께 적용된 실험이 많아 개별 최적화의 효과를 분리해 말하기 어렵다는 점이다. 메모리 풀, 예열, 복사 제거, 커널 퓨전, 중간 결과 복사 제어, affine 연산의 GPU 내부 통합, backward_bound_gpu의 중복 계산 제거 등은 각각 관측값을 남기지만, 서로 다른 시점에 결합되었으므로 하나의 통합 버전으로 묶어 단일 최적화의 효과로 서술할 수 없다. memcpy 호출 횟수 감소와 커널 호출 감소도 동일한 수치로 다루지 않으며, 전체 커널 호출 수가 특정 비율로 감소했다는 근거는 없다.

측정 범위와 예열 조건의 불확실성도 해석을 제한한다. 예열과 측정 범위 변화로 약 50ms가 줄어든 기록이 있어, 측정 밖으로 옮겨진 초기화 비용과 계산 개선을 구별해야 한다. 또한 실행 시간 스파이크와 예열 조건의 불확실성이 남아 있어, 가속 성과를 해석할 때 어떤 조건을 통제해야 하는지 명확히 정리해야 한다. 동일 초기화·예열 경계로 CPU/GPU 및 초기/후기 구현을 재측정하는 작업이 필요하다.

수치 정확성과 재현성 조건도 아직 충분히 검증되지 않았다. FP32로 바꿔 본 사실과 전체 입력 중 일부 검증 결과가 달라질 수 있어 재시험과 분석이 필요하다는 기록이 있으나, 이는 실제 오류 개수나 실패율을 측정한 결과가 아니다. FP32 전환의 성능과 검증 결과 일치 여부는 추가 확인이 필요하다. 전체 입력의 수치 정확성 및 검증 결과 일치를 확인하는 추가 검증이 필요하다.

비교 지표의 조건 분리도 여전히 과제로 남는다. 단일 샘플 지연, sparse.py 대비 평균 bound 계산의 구간별 가속비, 준비된 데이터셋의 배칭 처리량은 서로 다른 의미를 가지며, 배칭 처리량의 개선을 단일 요청 응답 지연이나 실시간성 입증으로 확대하지 않는다. cudaGraph와 배칭 관련 기록에는 약·정도 표현이 사용되었으므로, 이를 확정 평균으로 격상하지 않는다. 실제 입력 도착 조건에서 단일 요청 지연과 꼬리 지연을 평가하는 작업도 남아 있다.

외부 라이브러리 활용도 조건 의존적이다. cuBLAS와 cuSPARSE는 당시 모델 크기와 호출 패턴에서 느려져 기준 코드에 포함되지 않았으므로, 라이브러리 적용 여부는 모델 크기와 호출 패턴에 따라 판단해야 한다. 단일 스트림과 단일 데이터 복사가 현재 큰 병목으로 기록되어 있고, 배칭과 다중 스트림 관련 실제 환경과의 괴리를 후속 과제로 제시한 기록도 있다. 따라서 후속 검증에서는 동일 측정 경계의 재측정, 전체 입력의 수치 정확성 검증, 실제 입력 도착 조건에서의 지연 평가가 필요하다.

## 제6장 결론

본 연구는 안테나 선택 신경망의 CROWN 검증 계산을 GPU로 이식하는 과정에서 메모리 관리, 데이터 이동, 커널 실행 경로를 개선하고 그 성능 관측을 분석하였다. 초기 GPU 실행이 CPU 실행보다 오래 걸린 사례와 이후 구현에서 나타난 변화를 함께 보면, 검증 계산의 GPU 가속은 연산 병렬화와 함께 할당·복사·실행 비용을 검토할 필요성을 시사한다. 본 연구는 이 관점을 바탕으로 버퍼 재사용, 불필요한 복사 제거, 커널 통합 등의 변경을 정리하였다. 다만 여러 변경이 함께 적용된 실험으로부터 특정 요인의 영향이 다른 요인보다 크다고 결론 내리지는 않는다.

대표 성과로는 메모리 풀과 예열이 적용된 후기 단일 실행의 13.939ms 관측, 그리고 별도의 sparse.py 대비 평균 bound 계산 비교에서 표기된 forward 5.32배와 backward 5.30배의 가속비가 있다. 전자는 입력 버퍼를 재사용하고 초기 상태를 GPU에서 생성한 버전의 관측이며, 후자는 n=5 기준 비교표의 구간별 평균 지표다. 두 결과는 측정 범위가 같지 않으므로 하나의 전체 가속비로 합치지 않는다. 초기 실행과 후기 실행의 시간 차이 역시 초기화·예열 경계가 같다고 확인된 비교는 아니라는 점에서, 계산 자체의 개선과 측정 범위 변화의 영향을 구분하여 해석해야 한다.

이 결과의 의미는 특정 최적화의 보편적 우위를 입증하는 데 있기보다, 검증 계산을 GPU에서 실행할 때 함께 검토해야 할 구현 비용을 드러내는 데 있다. cuBLAS와 cuSPARSE는 시험된 조건에서 기준 코드에 포함되지 않았고, 배칭의 시간 감소는 준비된 데이터 조건에서 기록되었다. 라이브러리 선택과 배칭의 효용은 따라서 적용 조건과 함께 판단해야 한다. 또한 복수 변경 실험, 실행 시간의 변동, 전체 입력 정확성의 미확인으로 인해 개별 최적화 효과와 실제 요청 처리 성능에 관한 해석에는 한계가 있다.

후속 검증에서는 먼저 초기화·예열·측정 구간을 통일하여 CPU·GPU와 초기·후기 구현을 재측정하고, 주요 변경을 분리한 비교를 통해 각 변경의 영향을 살펴볼 필요가 있다. 다음으로 전체 입력에 대한 수치 정확성과 검증 결과 일치를 확인해야 한다. FP32 전환은 일부 결과가 달라질 가능성을 재시험할 과제로 남아 있다. 마지막으로 실제 입력 도착 조건에서 단일 요청 지연과 꼬리 지연을 평가하여, 준비된 데이터의 배칭 성과가 실제 활용 조건에서 어느 범위까지 이어지는지 검증해야 한다. 이 과정을 통해 관측된 구현 개선과 실시간 활용 가능성의 관계를 구체화할 수 있다.
