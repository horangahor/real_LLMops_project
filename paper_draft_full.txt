# CROWN 신경망 검증을 위한 GPU 가속 및 메모리 계층 최적화 기법 연구

## 제1장 서론

안테나 선택 신경망의 검증 계산을 하드웨어에서 실행하는 것은 실시간 활용 가능성을 탐색하는 한 사례가 된다. 이 연구는 해당 신경망의 정방향 통과와 backward 계산을 포함한 구현을 CUDA로 재작성하는 과정에서, GPU 실행이 계산 병렬화만으로 기대한 비용 절감으로 이어지지 않을 수 있다는 문제를 다룬다. 초기 관측에서는 GPU 실행이 CPU 실행보다 오래 걸렸고, 이후 입력 버퍼 재사용이나 초기 상태의 GPU 생성과 같이 실행 경로를 바꾸는 변경이 적용되었다. 이러한 관측은 GPU 이식에서 실행 비용을 해석할 때 계산 병렬화와 함께 메모리·데이터 이동·실행 경로의 영향을 함께 살펴야 함을 시사한다.

이 연구의 목표는 안테나 선택 신경망이라는 특정 사례를 중심으로, 검증 계산의 GPU 이식에서 나타나는 실행 비용을 계산 병렬화와 메모리·데이터 이동·실행 경로의 관점에서 함께 검토하는 데 있다. 구현 측면에서는 정방향 통과와 backward 계산을 포함한 CUDA 재작성 과정에서 실행 경로를 바꾼 후기 구현의 관측을 정리하고, 평가 측면에서는 단일 실행 관측과 구간별 평균 비교, 준비된 데이터의 배칭 결과를 측정 범위별로 구분해 해석한다. 다만 실시간 제약 달성이나 모든 신경망으로의 일반화는 이 연구에서 입증되지 않았으며, 각 변경의 독립 효과를 분리한 비교와도 구별하여 다룬다.

연구 범위는 안테나 선택 신경망의 검증 계산을 CUDA로 옮기는 과정에서 확인된 실행 관측과 그 해석에 한정한다. 논문 구성은 다음과 같다. 3장에서는 검증 계산의 기존 흐름과 GPU 이식에서 해결할 문제, 평가 범위를 정의한다. 4장에서는 메모리·데이터 이동과 커널·실행 경로의 변경 대상, 동작, 선택 이유를 설명한다. 5장에서는 단일 실행 관측, 구간별 평균 비교, 준비된 데이터의 배칭 결과를 측정 범위별로 구분해 제시하고 해석하며, 개별 효과 분리와 실제 입력 조건 관련 한계를 함께 논의한다.

## 제2장 관련 연구

## 제3장 배경 지식 및 문제 정의

### 3.1 배경 개념

이 연구의 대상은 안테나 선택 신경망의 검증 계산을 실제 하드웨어에서 수행할 가능성이다. 여기서 검증 계산은 신경망의 출력을 단순히 평가하는 것이 아니라, 주어진 입력 영역 전체에서 네트워크의 동작이 특정 조건을 만족하는지 확인하는 계산을 뜻한다. 이러한 검증은 일반적인 추론보다 계산량이 크며, 신경망의 각 층에서 입력 영역이 어떻게 변환되는지를 추적해야 한다. 따라서 검증 계산을 효율적으로 수행하려면 층별 연산의 흐름과 중간 결과의 처리 방식이 중요하다.

이 연구에서 다루는 검증 계산의 구체적 형태는 정방향 통과와 backward 계산을 함께 포함한다. 정방향 통과만으로는 입력 영역의 전파를 충분히 다루기 어렵거나, 검증에 필요한 경계 정보를 얻기 위해 추가적인 backward 계산이 필요할 수 있다. 이러한 계산 구성은 CPU와 GPU에서 관측된 초기 실행의 범위에도 반영되어 있다. 다만 이 장의 목적은 특정 버전의 구현 세부사항을 정리하는 것이 아니라, 검증 계산이 어떤 종류의 연산으로 이루어져 있고 어떤 계산 흐름을 따르는지 개념적으로 정리하는 데 있다.

한편 CROWN은 이 연구에서 검증 계산과 관련하여 언급되는 표기이다. 그러나 이 근거만으로는 CROWN의 수학적 정의나 관련 외부 이론을 추가로 서술하지 않는다. 검증 계산의 개념을 설명할 때 필요한 범위는 신경망 검증의 일반적 성격과 이 연구의 계산 구성에 한정하며, 약어의 풀이나 이론적 배경을 임의로 확장하지 않는다.

### 3.2 기존 계산 흐름

기존 구현은 검증 계산을 CPU 환경에서 수행하도록 구성되어 있으며, 이후 GPU로 이식하는 방향이 검토된다. 관측된 초기 실행은 정방향 통과와 backward 계산을 포함하는 형태로 나타난다. 이는 검증 계산이 단일 방향의 추론만으로 끝나지 않고, 층별 경계나 민감도와 관련된 정보를 backward 방향으로 처리하거나 조합해야 할 수 있음을 시사한다.

기존 계산 흐름에서 주목할 점은 연산 자체뿐 아니라 계산의 구성과 데이터 이동 방식이다. CPU에서 수행되던 계산을 GPU로 옮길 때는 커널 실행 방식, 메모리 배치, 데이터 전송과 같은 요소가 함께 달라진다. 따라서 GPU 이식에서는 단순히 같은 수식을 병렬 장치에서 실행하는 것만으로는 충분하지 않고, 기존 계산이 어떤 순서로 어떤 결과를 주고받는지 먼저 파악해야 한다. 이 장은 이러한 기존 흐름을 바탕으로 GPU 이식에서 무엇을 보존해야 하고 무엇을 다시 설계해야 하는지를 정리하기 위한 토대를 마련한다.

다만 초기 실행 관측은 특정 시점의 실행 범위를 반영한 것이며, 측정 범위가 다른 후기 실행이나 다른 입력 조건을 동일한 조건으로 간주해서는 안 된다. 또한 기존 계산의 세부 구현 방식, 반복 횟수, 소프트웨어 버전, 하드웨어 사양과 같은 정보는 이 장의 근거로 확인되지 않았으므로, 필요한 경우 확인 필요로 남긴다.

### 3.3 문제 정의

이 연구가 정의하려는 문제는 안테나 선택 신경망의 검증 계산을 GPU 환경에서 수행할 때, 기존 계산 흐름을 어느 범위에서 유지하고 어느 부분을 다시 구성해야 하는지 명확히 하는 것이다. 이를 위해 먼저 검증 계산의 입력과 출력을 정리해야 한다. 입력은 신경망에 주어지는 입력 영역 또는 그 영역의 표현이며, 출력은 검증 조건에 따라 결정되는 계산 결과 또는 중간 경계 정보일 수 있다. 이 입력과 출력의 관계가 기존 계산 흐름에서 어떻게 형성되는지 파악해야 GPU 이식의 평가 범위를 정할 수 있다.

다음으로 GPU 이식에서 확인할 조건을 정리한다. 첫째, 계산의 정확성이다. GPU로 옮긴 뒤의 결과가 기존 계산과 같은 의미를 갖는지, 정밀도 변경이 전체 입력 검증 결과에 어떤 영향을 주는지 확인해야 한다. 둘째, 재현성이다. 동일한 조건에서 반복 실행했을 때 결과가 일관되게 얻어지는지 검토할 필요가 있다. 셋째, 평가 범위이다. 초기 실행에서 관측된 정방향 통과와 backward 계산을 기준으로 하되, 측정 범위가 다른 실행이나 후기 관측값을 같은 조건처럼 비교하지 않도록 평가 범위를 제한해야 한다.

이 문제 정의에서 아직 확인되지 않은 사항도 함께 명시한다. 정밀도 변경과 전체 입력 검증 결과의 일치 여부, 그리고 재현성은 추가 확인이 필요한 과제이며, 이를 실제 검증 실패율이나 확정된 성능 차이로 해석해서는 안 된다. 또한 GPU 이식의 구체적 성능 비교, 버전별 실행 시간, 구현 최적화의 상세 효과는 이 장이 아니라 이후 장에서 다룬다. 따라서 이 장은 검증 계산의 기존 흐름과 GPU 이식에서 해결해야 할 문제, 그리고 평가 시 지켜야 할 조건을 정리하는 데 초점을 둔다.

## 제4장 연구 방법론 및 커널 최적화 설계

### 4.1 전체 구조

이 장은 GPU 가속 파이프라인의 변경 대상을 메모리·데이터 이동과 커널·실행 두 경로로 나누어 설명한다. 전체 구성은 기존 CPU 기반 검증 계산의 흐름을 보존하되, 장치 간 이동과 장치 내 실행에서 반복적으로 나타나는 비용을 줄이는 방향으로 설계한다. 파이프라인의 기본 골격은 정방향 통과와 backward 계산을 함께 처리하는 기존 계산 순서를 유지하며, 그 위에서 버퍼 배치, 전송 시점, 커널 호출 구조를 다시 정리한다.

전체 구조를 결정할 때 우선한 기준은 두 가지이다. 첫째, 계산 결과의 의미와 층별 전파 순서를 바꾸지 않는 것이다. 둘째, 측정 구간 밖에서 드러나는 초기화·예열 효과와 구간 안에서 드러나는 데이터 상주·실행 개선을 섞지 않는 것이다. 이 기준 때문에 이 장의 설명은 개별 변경의 동작과 선택 이유를 밝히는 데 집중하고, 각 변경의 독립적인 가속비나 전체 성능 수치를 여기서 합산해 주장하지 않는다. 정량 비교와 측정 조건은 5장으로 분리한다.

구성의 핵심은 두 층으로 볼 수 있다. 메모리·데이터 이동 층은 할당, 상주, 버퍼 재사용, 전송 제거를 다룬다. 커널·실행 최적화 층은 커널 구성, 중간 결과 처리, 라이브러리 사용 방식, 실행 흐름을 다룬다. 두 층은 서로 독립적이기보다 함께 변경되므로, 한 층의 효과를 다른 층의 효과와 분리하지 않은 상태에서는 단일 원인으로 해석하지 않는다. 예를 들어 버퍼 재사용과 커널 퓨전이 함께 적용된 경우, 관측된 변화는 계산 병렬화만이 아니라 할당·복사·실행 비용의 조합이 반영된 결과로 본다.

이 장의 서술 순서는 설계 동기에서 시작해 전체 구성을 제시한 뒤, 세부 동작과 선택 이유를 설명하는 방식으로 진행한다. 구현된 방법뿐 아니라 검토했으나 효과가 확인되지 않았거나 아직 독립된 성과로 정리되지 않은 접근도 함께 기록한다. 다만 자료에 없는 메모리 풀 크기, 잠금 구현, 스트림 개수와 같은 세부 구현 값은 이 장에서 만들어 쓰지 않는다. 필요한 값은 [확인 필요]로 남긴다.

### 4.2 메모리·데이터 이동

메모리·데이터 이동에서 다룬 변경 대상은 초기화 비용, 상주 전략, 불필요한 복사, 전송 시점이다. 이 변경의 공통 동기는 측정 구간 안에서 반복되는 할당·복사·전송을 줄이고, 한 번 확보한 데이터를 이후 계산에서 다시 사용할 수 있게 하는 데 있다. 다만 예열로 인해 측정 구간 밖으로 이동한 초기화 비용과 계산 자체의 개선을 구별해야 하므로, 데이터 상주나 예열 효과를 하나의 독립 성과로 귀속하지 않는다.

먼저 메모리 할당과 상주 방식을 검토했다. 검토 대상에는 메모리 풀 유지, 예열 이후 zero 초기화, 결과 버퍼의 불필요한 복사 제거, 가중치의 양수부와 음수부를 모두 상주시키는 방식, forward 결과의 장치→호스트 복사 제거가 포함된다. 이 항목들은 서로 다른 구현 선택이므로 하나의 단일 변경으로 합쳐 설명하지 않는다. 예를 들어 결과 버퍼 복사 제거와 forward D2H 복사 제거는 모두 전송량을 줄이는 방향이지만, 적용 위치와 영향이 다를 수 있어 별도로 기록한다.

버퍼 재사용도 이 층의 중요한 변경이다. forward 입력 버퍼를 backward에서 재사용하는 구현과, 초기 상태를 GPU에서 생성하는 구현이 검토되었다. 이 방식은 장치 간 이동이나 재할당 빈도를 줄일 가능성이 있지만, 이 변경만의 독립적인 가속비로 설명하지는 않는다. 버퍼 재사용은 커널 실행 구조나 데이터 흐름의 다른 변경과 함께 평가되어야 하므로, 여기서는 재사용의 의도와 적용 위치만 서술한다.

데이터 전송 측면에서는 불필요한 호스트 전송을 줄이는 방향이 검토되었다. 특히 forward 결과를 매번 호스트로 복사하는 대신 필요한 시점까지 장치 측에 유지하거나, 검증 계산에 실제로 필요한 결과만 전송하는 구성을 고려했다. 이러한 전송 제거는 측정 구간 안의 데이터 이동 비용을 줄일 수 있으나, 어떤 결과가 장치 측에 남아도 되는지, 어떤 시점에서 호스트 전달이 필요한지는 계산 의미에 따라 달라진다. 따라서 전송 제거는 계산 흐름의 재정의와 함께 판단해야 하는 선택으로 본다.

이 층의 설계에서 주의한 점은 상주·재사용·전송 제거를 서로 독립적인 검토 항목으로 다루는 것이다. 예열은 측정 준비 과정에서 나타날 수 있는 요소이므로, 예열 자체를 데이터 상주의 효과로 해석하지 않는다. 또한 메모리 풀의 구체적 크기나 잠금 방식, 스트림 개수처럼 자료에 확인되지 않은 구현 세부사항은 이 장에서 덧붙이지 않는다. 필요한 경우 [확인 필요: 메모리 풀 크기], [확인 필요: 스트림 구성]과 같이 표시하되, 추정으로 단정하지 않는다.

### 4.3 커널·실행 최적화

커널·실행 최적화에서는 커널 구성, 중간 결과 처리, 라이브러리 사용, 실행 흐름을 다시 설계했다. 이 층의 목적은 장치 내 실행에서 반복되는 계산과 복사를 줄이고, 호출 구조를 정리하는 데 있다. 다만 커널 제거와 전체 커널 호출 감소율, memcpy 호출 감소는 서로 다른 수준의 변화이므로, 여기서 하나로 묶어 일반화하지 않는다.

검토된 커널·실행 변경에는 커널 퓨전, set_shape 내장, alpha/beta 풀 유지, 중간 결과 복사 제어, affine의 GPU 내부 통합이 포함된다. 이와 함께 backward_bound_gpu에서 affine의 중복 계산을 제거해 커널 함수 두 개를 줄였다는 기록도 있다. 이 기록은 특정 경로에서 함수 수가 줄어든 사실을 보여주지만, 이것이 곧바로 전체 커널 호출 감소나 memcpy 호출 감소로 이어진다고 단정하지는 않는다. 함수 수 감소와 호출 횟수 감소는 구별해서 해석해야 한다.

라이브러리 사용은 시험된 모델 크기와 호출 패턴에서 평가했다. cuBLAS와 cuSPARSE는 이 조건에서 기준 코드보다 느려져 기준 코드에 포함하지 않았다. 이 결과는 해당 모델 크기와 호출 패턴에서의 관측에 한정되며, 라이브러리의 보편적 우열로 확대하지 않는다. 즉 어떤 조건에서 cuBLAS나 cuSPARSE가 유리할 수 있는지 일반화하기보다, 이 연구의 시험 조건에서 기준 경로로 채택하지 않은 이유를 기록하는 데 그친다.

실행 흐름 측면에서는 중간 결과의 생성과 소비 순서를 조정해 불필요한 복사와 대기 지점을 줄이는 방향을 검토했다. 중간 결과 복사 제어는 커널 간 데이터 전달 방식에서 중요한 요소이며, affine의 GPU 내부 통합은 장치 내에서 처리되는 계산 단위를 정리하는 시도로 볼 수 있다. 이러한 변경은 실행 흐름을 단순화하고 장치 내 이동량을 줄일 가능성이 있지만, 실제 효과는 커널 구성, 버퍼 배치, 전송 제거와 함께 나타난다. 따라서 여기서는 각 변경의 역할과 선택 이유를 설명하고, 효과 크기의 상세 비교는 5장에 남긴다.

이 층에서 아직 독립된 성과로 정리하지 않은 접근도 함께 명시한다. 예를 들어 특정 커널 제거가 전체 호출 감소로 얼마나 이어졌는지, memcpy 호출 감소가 어느 경로에서 주로 발생했는지는 별도 확인이 필요한 사항이다. 또한 커널 퓨전이나 함수 수 감소가 항상 동일한 방향의 성능 변화로 이어진다고 보지 않으며, 측정 조건과 입력 범위에 따라 해석이 달라질 수 있음을 전제한다. 구현 세부사항 중 자료에 없는 항목, 예를 들어 커널 launch 구성이나 스트림 활용 방식은 [확인 필요]로 남긴다.

전체적으로 커널·실행 최적화는 계산 자체의 개선과 실행 조직화를 함께 다룬다. 그러나 이 장의 관측은 여러 변경이 함께 적용된 상황을 반영하므로, 계산 병렬화보다 메모리 설계의 영향이 더 크다는 식의 원인 단정은 하지 않는다. 대신 계산 병렬화와 함께 할당·복사·실행 비용을 함께 고려할 필요가 있음을 시사하는 수준으로 서술한다.

## 제5장 실증 평가 및 결과 고찰

### 5.1 실험 설계

이 장의 평가는 CUDA로 재작성된 정방향·backward 계산 경로의 실행 특성을, 측정 범위와 비교 대상이 서로 다른 여러 관측으로 나누어 살펴보는 데 목적이 있다. 실험 환경은 CUDA 기반 GPU 실행과 기존 CPU 기준 실행을 함께 두고, 단일 실행 관측, 구간별 평균 비교, 준비된 데이터의 배칭 처리라는 세 종류의 측정 관점을 구분한다. 비교 대상은 구현 단계에 따라 초기 관측, 후기 단일 실행 관측, sparse.py 대비 평균 bound 계산, 추론·bound·검증 구간 비교, 준비된 데이터셋의 배칭 처리, 단일 스트림 입력 복사 실험으로 나뉜다. 각 비교는 동일한 가속비를 공유하지 않으며, 측정 구간과 입력 조건이 다르면 결과를 같은 척도로 묶지 않는다.

평가 지표는 실행 시간 관측과 구간별 평균 시간, 그리고 준비된 데이터 조건에서의 배칭 처리 시간을 중심으로 한다. 단일 실행 관측은 특정 실행 화면의 값을 기록한 것이므로 초기 구현과의 차이를 동일 조건의 CPU 대비 가속비로 해석하지 않는다. 구간별 평균 비교는 bound 계산처럼 반복 측정된 평균을 다루지만, 단일 실행이나 전체 서비스 처리 성능과는 측정 범위가 다르다. 배칭 처리 시간은 준비된 데이터셋에서 얻은 기록으로, 실제 요청 도착 조건에서의 지연이나 꼬리 지연을 대신하지 않는다. 정밀도 변경 이후의 결과 일치 여부와 실행 시간 재현성은 이 장의 평가 범위에 포함하지 않고 후속 검증 과제로 남긴다.

표 5-1은 정방향 통과와 backward 계산을 포함한 초기 관측으로, GPU 실행이 CPU 실행보다 오래 걸린 기록을 보여준다. 이 관측은 초기 구현 단계의 값이므로 예열 적용 후의 후기 결과와 측정 경계가 같다고 보지 않는다. 표 5-2는 후기 단일 실행 관측으로, 입력 버퍼 재사용과 초기 상태의 GPU 생성을 포함한 특정 실행의 값이다. 이 값은 특정 실행의 관측이며, 초기 실행과의 차이를 동일 조건의 CPU 대비 가속비로 계산하지 않는다.

표 5-3은 sparse.py와 CUDA의 평균 bound 계산을 비교한 것으로, 두 방향 모두 CUDA의 bound 계산이 짧게 기록된 n=5 기준 값이다. 여기서 bound 구간의 평균과 추론·bound·검증 구간의 가속비는 서로 다른 지표이므로, bound 계산 가속비를 다른 구간의 가속비로 대체하지 않는다. 표 5-4는 추론·bound·검증 구간을 별도로 비교한 값으로, 동일 원문 표에서 bound 계산 가속비와 구분되어 표기된 지표다. 이 표는 구간별 평균과 단일 실행, 전체 서비스 처리 성능의 측정 범위가 다르다는 점을 함께 보여준다.

표 5-5는 준비된 데이터셋에서 배칭을 적용한 뒤 전체 처리 시간이 감소한 기록을 담고 있으며, cudaGraph로 추론과 bound를 따로 캡처한 실험의 시간 감소 메모도 함께 존재한다. 이 값은 약·정도로 기록된 관측이므로 확정 평균이나 단일 요청 지연으로 해석하지 않는다. 표 5-6은 단일 스트림 입력 복사 실험의 관측으로, 크기 계산·복사 등을 적용한 실행이 graph 기본 실행보다 오래 걸렸고 이후 forward·backward 양상도 달랐던 결과를 보여준다. 이 실험은 계측·복사·메모리·검증 자료구조 변경이 함께 적용되어 있어, 시간 차이를 특정 변경 하나의 독립 효과로 분리하기 어렵다.

추가로, cuBLAS와 cuSPARSE는 시험된 모델 크기와 호출 패턴에서 느려져 기준 코드에 포함하지 않았다. 이는 해당 조건에서 라이브러리 선택을 달리한 결과이며, 다른 조건에서의 일반적 우열을 뜻하지 않는다. 정밀도 변경 뒤 전체 입력 검증 결과의 일치 여부와 실행 시간의 재현성은 아직 측정되지 않았으므로, 이 장의 결과로 확정하지 않는다.

### 5.3 한계와 미해결 문제

이 장의 결과 해석은 측정 범위와 조건 의존성을 분리해 읽는 데 달려 있다. 초기 관측과 후기 예열 적용 결과는 측정 경계가 같다고 확인되지 않았고, 측정 밖으로 옮겨진 초기화 비용과 계산 자체의 개선은 서로 다른 효과다. 후기 단일 실행 관측은 특정 실행의 값이므로 초기 구현과 동일 조건의 가속비를 입증한 비교가 아니다. 구간별 평균, 단일 실행, 배칭 처리, 전체 서비스 처리 성능은 각각 측정 범위가 달라 하나의 누적 최적화 단계로 합쳐 해석하기 어렵다.

단일 스트림 입력 복사 실험에서는 계측·메모리·복사·검증 자료구조 변경이 함께 존재해, 시간 차이를 특정 요소 하나의 원인으로 분리할 수 없다. 배칭 처리 시간 감소는 준비된 데이터 조건에서 약·정도로 기록된 관측이며, 실제 입력 도착 조건의 요청 지연이나 꼬리 지연을 평가한 결과는 아니다. cuBLAS와 cuSPARSE의 제외는 시험된 모델 크기와 호출 패턴에서의 선택 결과이므로, 다른 조건에서의 라이브러리 선택으로 일반화할 수 없다. 정밀도 변경 이후의 결과 일치 여부와 실행 시간 재현성은 후속 검증 과제이며, 실제 실패율이나 확정된 정확성 성과는 아직 측정되지 않았다.

연구는 안테나 선택 신경망 검증의 하드웨어 실행과 실시간 활용 가능성을 탐색하는 데 초점이 있으나, 실시간 제약 달성과 실제 입력 조건의 단일 요청 지연·꼬리 지연은 추가 평가할 범위로 남는다. 따라서 이 장의 결과는 특정 조건과 측정 범위에서 얻은 관측으로 읽고, 조건 의존성과 개별 효과 분리의 한계를 함께 고려해야 한다.

## 제6장 결론

이 연구는 CUDA 기반 GPU 검증 구현이 계산 병렬화만으로 설명되지 않는 실행 비용 구조를 드러낸다는 점에서 출발한다. 관측된 변화는 커널 연산의 병렬화와 함께 할당·복사·실행의 비용이 전체 성능에 함께 작용함을 시사하며, 이는 GPU 검증 가속을 해석할 때 계산 병렬화만을 기준으로 삼기 어렵다는 점을 보여준다. 즉, 구현 변경의 효과는 연산 자체의 개선뿐 아니라 준비 단계와 데이터 이동, 실행 경로의 선택이 함께 반영된 결과로 읽어야 한다.

대표 성과로는 후기 단일 실행에서 13.939ms가 관측된 점과, 별도의 sparse.py 대비 평균 bound 계산 비교(n=5)에서 forward 5.32배, backward 5.30배의 가속비가 표기된 점을 들 수 있다. 다만 이 두 수치는 같은 비교로 묶을 수 없다. 13.939ms는 메모리 풀과 예열이 명시된 후기 단일 실행의 관측이며, 입력 버퍼 재사용과 초기 상태의 GPU 생성이 포함된 특정 실행의 값이다. 반면 평균 bound 가속비는 sparse.py와의 별도 비교에서 얻은 평균 지표이므로, 후기 단일 실행의 비교비나 전체 서비스 수준의 가속비로 해석해서는 안 된다. 두 지표는 측정 경계와 비교 대상이 다르므로, 각각이 무엇을 보여주는지 구분하여 읽어야 한다.

이 연구의 해석은 여러 변경이 함께 적용된 관측에 기반하므로, 초기화·예열·측정 범위의 변화와 계산 자체의 개선을 구별해야 하며, 개별 요인의 상대적 영향 크기를 단정할 수는 없다. 배칭 성과는 준비된 데이터 조건에서 기록된 결과이므로, 단일 요청의 지연이나 실제 입력 환경의 실시간성으로 바로 확대하지 않는다. 또한 외부 라이브러리 선택의 결과는 시험된 모델 크기와 호출 패턴에 의존하므로 보편적 우위로 보기 어렵고, 전체 입력의 수치 정확성과 검증 결과 일치, 실행 시간의 재현성은 아직 후속 검증이 필요한 과제로 남는다. 정밀도 변경 가능성을 측정된 실패율로 바꾸어 해석해서도 안 된다.

따라서 후속 작업에서는 먼저 같은 측정 경계에서 초기 비교와 후기 실행의 조건을 다시 정렬하여, 관측된 차이가 준비 단계의 변화인지 계산 병렬화의 효과인지 재확인할 필요가 있다. 이어서 전체 입력에 대한 수치 정확성과 검증 결과의 일치를 확인하고, 실행 시간의 재현성을 점검해야 한다. 마지막으로 준비된 데이터가 아닌 실제 입력 도착 조건을 반영한 지연 평가로 확장하여, 배칭 성과와 단일 요청 지연 사이의 간극을 구체적으로 검토할 필요가 있다. 안테나 선택 신경망 검증의 하드웨어 실행과 실시간 활용 가능성은 탐색 단계로 이해할 수 있으나, 이를 실시간 달성이 입증된 연구로 확대하지는 않는다.
