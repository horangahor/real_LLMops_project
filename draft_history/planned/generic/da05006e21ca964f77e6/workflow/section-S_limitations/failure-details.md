- [editorial; 처리 책임: editor] 이전 지적(finding-8)에서 측정 블록 분리, Pinned/No-Pin 경로 차이, 구성 요소별 역할, 결합 방식, 커널 감소, 방법 A/B/C 설계 설명 등이 길게 나열되지만 소절 목적 대비 ‘비교 조건 통제의 한계’로 수렴하는 종결이 약하다고 지적했으나, 현재 문단에서도 나열 후 한계 해석으로 돌아오는 문장 정리가 여전히 부족하다.
  - 문단: S_limitations_p24; 근거: 미지정
  - 실제 본문: 비교 조건 통제의 한계는 측정 블록이 서로 다른 구성으로 분리되어 있다는 점에서 먼저 드러난다. Host Alloc(Pinned Memory) 결과와 nopin(Pageable Memory) 결과는 별도 측정 블록으로 나누어 비교했으며, 각 블록은 Real-Time Single-Sample(B=1) Latency Analysis와 Phase Timing Breakdown을 포함한다. 이 구조 덕분에 평균 지연시간, 최대 지연시간, 지터 같은 지표를 블록별로 확인할 수 있지만, 블록 간 비교가 단일 실행 기록 중심으로 정리되어 있어 동시 변경의 효과를 분리하기 어렵다. Pinned Memory는 PCIe DMA 엔진을 통해 GPU로 전송하는 경로로 설명되고, No-Pin(Pageable)은 CPU가 드라이버 내부 스테이징 버퍼로 동기식 memcpy를 수행하는 경로로 설명되는데, 이러한 경로 차이는 작은 전송에서 DMA 셋업 오버헤드 누적 때문에 Pinned가 infer 단계에서 더 느리게 측정될 수 있다는 서술과 함께 제시된다. 실제로 Pinned Memory는 평균 처리 속도에서는 미세하게 불리할 수 있으나, OS 페이징 간섭을 차단하여 최대 지연과 지터를 억제하는 안정성 관점의 역할로 서술된다. 한편 가중치를 GPU에 사전 업로드하여 memcpy를 줄이려는 시도는 측정 결과 큰 의미 있는 차이를 만들지 못했다고 기록되며, cuSPARSE SpMV/SpMM을 network_forward()의 W*x에만 부분 적용했을 때는 descriptor·buffer 처리 비용과 매 호출마다 cusparseDnVec 생성·삭제, buffer size 계산, layer마다 D2H→CPU vec_add→H2D 수행이 추가되어 전체 24ms 중 일부만 영향을 받는 구간에 오버헤드가 더해졌다. forward-backward 간 전달되는 alpha/beta 값을 메모리 풀에 올려 전달 과정을 삭제하고, 레이어별 alpha/beta GPU 버퍼를 메모리 풀에 추가해 forward에서 GPU에 저장, backward가 host ForwardBoundResult에서 H2D 복사하지 않고 GPU 버퍼를 직접 사용하며 alpha/beta 저장용 D2D 복사 4회를 cache_relaxation_layer_gpu 1회로 통합한 변경도 측정값과 함께 기록되지만, 이러한 개별 최적화가 결합되는 방식이나 상호작용 효과는 구성 요소 나열 수준에서 확인될 뿐 결합 구조나 연결 방식이 직접 기술되지 않는다. 초기화만 하면 forward, backward의 bound 계산 시간은 비슷하며(약 0.2ms 차이), Nvidia warm up 가이드라인을 세워 실제 사이클 시간만 측정하고 warm up을 한 번 하며 CV를 통해 스파이크·분산을 규명하기로 했고, 추론·bound 계산·검증 3가지 값을 나눠서 측정했다는 서술도 있으나, 실시간 PCIe H2D 전송 최적화를 위해 Host Memory Pinning(cudaHostRegister)을 적용해 일반 메모리를 복사 없이 pinned Memory로 승격시켜 GPU가 CPU 메모리에 직접 접근할 수 있도록 했으며, 커널 memcpy에서 기존에 MAXDIM으로 무조건 512개의 float만큼 복사하던 것을 필요한 만큼의 데이터 크기만 복사하도록 고친 변경은 N > 0 조건에서만 유효하게 기록된 관찰로, 측정 조건 통제가 충분히 분리되지 않은 상태에서 기록된다. CROWN 3가지 방법에서 사용하는 커널의 퓨전 및 backward_only에서 메모리 복사 커널을 제거해, 3-layer 네트워크 기준으로 Forward method=0 bound 27→18회(9회 감소), Backward method=1 bound 전체 46→31회(15회 감소), Backward-only method=2 bound 전체 45→33회(12회 감소)가 되었고, graph mode=1에서 샘플 1개 전체 기준으로 Forward 33→24회(9회 감소), Backward 52→37회(15회 감소), Backward-only 51→39회(12회 감소)가 되었다는 커널 발사 횟수 감소도 보고되지만, 방법 B는 행렬 곱, ReLU 완화, 바운드 합산 등 CROWN의 모든 커널에 직접 blockIdx.z를 넣어서 3차원 배칭 커널을 작성하는 방식이고, 방법 C는 CROWN 연산 시간의 80% 이상이 행렬 곱셈(A×W)이므로 가장 무거운 행렬 곱셈만 cuBLAS(cuBlasSgemmBatched)에 맡기고 CROWN 전용 연산(ReLU 완화 계수 계산 등)은 방법 B의 자체 3D 커널로 돌리는 하이브리드 방식이라는 설계 설명 역시 구성 요소별 역할 서술에 가깝다. Pinned Memory는 데이터가 충분히 클 때 빠르다는 전제 조건이 있으며, 1,028 Byte(1 KB) 수준에서는 No-Pin(일반 메모리)이 더 빠를 수 있는데, 이는 CPU L1 캐시에서 드라이버 내부 버퍼로 복사하는 데 불과 20~30 나노초(0.00003 ms)면 끝나는 반면, Pinned Memory는 PCIe DMA 엔진에 명령 패킷을 쏘고 트랜잭션을 시작하는 하드웨어 오버헤드만 약 1~2 마이크로초(0.0015 ms)가 걸려 작은 데이터에서는 DMA 셋업 오버헤드가 누적되어 infer 단계에서 정확히 13초(132초 vs 119초)가 더 걸린 사례가 있었다는 서술도 측정 블록과 함께 제시된다. 구성 요소별 역할로는 cuBLAS는 NVIDIA GPU에서 선형대수 연산을 가속하는 라이브러리이며, 메모리 풀은 함수 호출마다의 메모리 할당·해제를 없애기 위해 큰 공간을 미리 할당해 빌려주는 방식으로 사용되고, 가중치(W) GPU 사전 업로드는 고정된 가중치를 네트워크 로드 시점에 미리 GPU에 올려 matmul 호출마다의 memcpy를 줄이려는 역할이며, 벡터 연산을 CPU로 돌리는 것은 matmul만 GPU로 실행하는 하이브리드 구성을 만들기 위한 역할로 설명된다. 결합 방식은 초기에는 cuBLAS로 matmul을 대체하고 메모리 풀을 사용하며 벡터 연산을 CPU로 돌리는 GPU 최적화 모드(MODE: GPU OPTIMIZED(cuBLAS + Pool))로 결합되었다가, 이후 matmul만 GPU로, 나머지를 CPU로 처리하는 하이브리드 모드(MODE: HYBRID(matmul=GPU, rest=CPU))로 바뀌었고, v2 적용 방안에서는 cuBLAS 예열(더미 matmul 호출로 초기화), 가중치 GPU 사전 업로드, 16×491 행렬 등 필요한 부분만 복사하도록 memcpy 범위를 줄이는 방식이 추가로 결합되었다고 기록된다. forward+backward 결합은 정방향과 backward 바운드를 함께 실행하는 방식으로 측정되며, backward_only는 backward 바운드만 실행하는 방식으로 측정되고, CUDA 그래프(cudaGraph) 적용 버전도 별도로 측정된다. backward_only가 forward+backward보다 빠르게 관측되었고, forward가 가장 느리게 관측되었으며, 이는 일반적인 예상(forward < forward+backward < backward_only)과 다른 실행 결과로 기록되었다. CUDA 그래프 적용 후 전체 소요 시간이 감소하였고(예: 787s → 630s, 1029s → 668s), Phase breakdown에서 bound 단계가 전체 elapsed의 대부분을 차지하고 infer 단계가 그 다음, certify 단계가 가장 작은 비중을 차지한다는 관측도 함께 제시된다. 구성 요소별 역할로 pinned Memory 추가, cudaEvent 제어, 필요한 만큼 계산해서 D2H memcpy, certify topk 자료구조 스택화가 각각 언급되지만, 구성 요소들의 결합 방식은 실제 구현·실행 원문에서 직접 기술된 결합 구조나 연결 방식이 확인되지 않는다. forward에서는 전체적(추론, bound, 검증)으로 graph 단일 적용이 우수하고 infer_s에서 약 20초 차이가 나며, backward에서는 total 시간이 비슷해지는 이유가 infer에서 깎인 약 20초를 bound에서 graph보다 약 20초 빨리 수행하기 때문이라고 서술되며, 위 이유로 일단 유지하기로 했다고 기록되어 있으나, 이는 실행 결과 해석·판단의 서술이지 구성 요소 간 상호작용의 측정 구조 자체를 직접 기술한 것은 아니다. 결국 이러한 구성은 각 요소의 역할과 관측 결과를 분리해 보여 주지만, 공정 비교를 위한 조건 통제와 결합 효과의 분리 측정이 충분히 명시되지 않아 비교 조건 통제의 한계로 남는다.
